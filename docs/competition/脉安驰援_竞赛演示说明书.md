# 脉安驰援竞赛演示说明书

副标题：共享急救设备、志愿者协同与个人健康管理移动应用

版本：1.0.0
文档日期：2026-08-09

## 1. 文档用途

本说明书用于中国大学生计算机设计大赛的软件现场演示、录屏和答辩。作品归入“软件应用与开发—移动应用开发（非游戏类）”。演示坚持真实账户、真实接口和真实数据库状态流转，不使用内置体验账号，不预置人物、设备、救援或健康记录。

## 2. 作品概述

脉安驰援面向公共场所急救设备共享难、紧急事件协同慢和个人健康信息分散三个问题，提供四项核心能力：共享 AED 与急救箱登记审核、附近志愿者协同救援、穿戴设备健康趋势、体检报告 OCR 与健康档案。

系统由 uni-app/Vue 3 移动端、Spring Boot 服务端和 MySQL 数据库组成。前端同一套页面组件服务普通用户、急救志愿者和平台审核员，角色专属入口由后端授权决定；共用业务页面不为三个门户重复实现。

## 3. 参演环境

### 3.1 软件要求

| 组件 | 建议版本 | 用途 |
| --- | --- | --- |
| Node.js | 20 LTS 或更高 | 前端依赖与构建 |
| Java | 21 | 服务端运行 |
| Maven | 3.9 或更高 | 服务端构建 |
| MySQL | 8.0 | 业务数据 |
| HBuilderX | 与 uni-app 编译器匹配 | iOS 打包 |

### 3.2 必要配置

1. 从 `.env.example` 和 `server/.env.example` 复制本地配置文件。
2. 为前端填写 HTTPS API 地址；需要地图选点和道路路线时填写高德 Web JS API 配置。
3. 为服务端设置数据库账号、随机 JWT 密钥和媒体目录。
4. OCR 与健康分析均为可选外部能力。未配置时系统必须显示不可用或人工录入入口，不能伪造结果。

### 3.3 首个管理员

空数据库第一次启动前，临时设置 `BOOTSTRAP_ADMIN_PHONE`、`BOOTSTRAP_ADMIN_PASSWORD` 和可选的 `BOOTSTRAP_ADMIN_NICKNAME`。密码不得少于 12 位。服务端只在数据库中不存在管理员时创建首个管理员。创建后立即移除手机号和密码变量并重启服务。

## 4. 参演账户准备

现场准备三个临时手机号，分别注册普通用户、志愿者候选和审核员候选。先用首个管理员登录，在“我的—账户权限”中把后两者分别授权为“急救志愿者”和“平台审核员”。两名目标用户退出并重新登录，使新 JWT 生效。

这些账户只存在于现场数据库，不写入源码、迁移脚本、说明书或 Git 历史。演示结束后删除现场数据库或按主办方要求留存脱敏记录。

## 5. 演示前检查

1. 三台手机或三个独立浏览器会话分别登录三种角色。
2. 打开定位权限，确认普通用户与志愿者页面显示当前实际位置。
3. 确认地图密钥有效；若道路规划不可用，主动说明系统不会绘制伪路线。
4. 准备一张已脱敏的体检报告图片，避免姓名、身份证号、条码和联系方式入镜。
5. 确认 OCR 与模型数据外发授权处于关闭状态，需要展示时由用户现场开启并确认提示。
6. 使用普通测试描述，不拨打 120，不触发真实急救机构，不宣称现场记录为真实病例。

## 6. 推荐演示流程

### 6.1 开场：问题与方案（约 40 秒）

说明公共 AED 的信息通常分散、维护状态不透明，突发事件中求救者、设备和志愿者缺少统一协同。脉安驰援把“设备可信登记—就近匹配—志愿者响应—双方完成确认—设备归还”做成可追踪闭环，并把日常健康趋势与体检档案纳入同一移动端。

### 6.2 设备登记与跨端审核（约 60 秒）

1. 普通用户进入“我的设备—添加急救设备”。
2. 选择固定 AED，填写名称、位置、有效期、开放时段和管理方，上传脱敏图片后提交。
3. 审核员进入“设备审核”，打开刚提交的记录并确认。
4. 普通用户返回设备列表，展示状态已同步更新；地图刷新后出现该设备。

讲解重点：这不是三端各存一份数据，设备记录只有一个数据库实体。提交、审核和地图展示共享同一状态；审核前设备不能进入调度候选。

### 6.3 呼救与 AED 匹配（约 70 秒）

1. 普通用户进入 SOS 页面，确认系统取得真实位置。
2. 选择症状和紧急程度，使用明确的测试描述发出呼救。
3. 进入救援详情，展示服务端返回的匹配阶段、AED、距离和预计到达时间。
4. 地图只展示高德规划的可通行路线。路线服务不可用时只保留资源与现场位置。

讲解重点：呼救先落库，再由服务端调度；同一求救者不能并行发起多条活动呼救；设备预留使用事务和版本控制，取消或失败会释放设备。

### 6.4 志愿者响应与信息分级（约 90 秒）

1. 志愿者进入“救援任务”并上报实际位置。
2. 接单前只看到附近任务的模糊位置和必要摘要，不显示精确地址、照片与联系电话。
3. 志愿者确认响应后，系统开放任务所需信息，并按“前往 AED—已取 AED—前往现场—已到达—开始救援—提交完成”推进。
4. 普通用户页面通过 SSE 或轮询同步每一步状态。

讲解重点：隐私信息随协作关系逐步开放；移动 AED 跳过固定设备的取用和归还环节。没有真实位置上报时，界面不会模拟移动或虚减 ETA。

### 6.5 完成确认、评价与归还（约 50 秒）

1. 志愿者提交完成，普通用户确认救援结束。
2. 展示救援总时长、关键事件时间线和评价入口。
3. 固定 AED 由志愿者确认归还，设备恢复可用；移动设备按其自身在线状态恢复。

讲解重点：完成不是单边按钮，双方确认和超时规则由服务端状态机约束；记录按同一救援编号在不同门户展示相应视图。

### 6.6 体检报告 OCR 与健康档案（约 60 秒）

1. 普通用户在设置中确认健康数据外发授权。
2. 进入“录入体检报告”，上传脱敏报告原图。
3. OCR 结果交给健康分析服务提取检查日期、机构和报告中实际出现的指标，不要求用户先创建常用指标。
4. 用户核对后保存，进入健康档案查看风险分级、异常指标和建议。

讲解重点：OCR 只负责识别文本，模型只做结构化整理与一般性健康信息说明。未配置外部服务时可人工录入；结果不能替代医生诊断。

### 6.7 科普投稿与审核（约 40 秒）

1. 普通用户提交一篇短科普内容。
2. 审核员在“投稿审核”中确认内容。
3. 普通用户刷新科普频道，展示审核后的文章；点赞和收藏通过后端接口持久化。

## 7. 核心创新点讲解

| 创新点 | 展示证据 |
| --- | --- |
| 固定与移动急救设备统一调度 | 同一地图、不同在线与归还规则 |
| 三角色协同但页面复用 | 同一登录体系、角色授权、共享业务实体 |
| 接单前后隐私分级 | 志愿者响应前后 DTO 信息差异 |
| 真实路线原则 | 高德规划成功才绘制道路，不做几何伪线 |
| 可靠救援状态机 | 事务预留、活动锁、幂等请求、双方确认 |
| OCR 与健康分析解耦 | OCR 识别、结构化分析、用户复核后入档 |

## 8. 异常情况处置

| 情况 | 现场处理 |
| --- | --- |
| 定位权限被拒绝 | 用户主动打开系统权限或主动选点，不使用固定坐标冒充当前位置 |
| 高德路线不可用 | 展示起终点并说明安全降级，不绘制伪路线 |
| OCR 不可用 | 切换人工录入，不展示伪识别结果 |
| 模型接口不可用 | 使用本地规则分析或仅保存报告，不显示厂商错误堆栈 |
| SSE 断开 | 客户端自动使用定时查询同步状态 |
| 重复点击呼救 | 客户端请求号与服务端活动锁阻止重复事件 |
| 账户刚变更角色 | 退出并重新登录，获取包含新角色的 JWT |

## 9. 安全与伦理说明

- 本作品用于辅助信息组织和救援协同，不能替代 120、专业急救人员或医疗诊断。
- 演示不得使用真实患者身份、未经同意的体检报告或真实紧急事件。
- 图片上传后由服务端重编码并清除 EXIF；私有媒体通过短时下载授权访问。
- 密码使用 BCrypt；接口使用 JWT；管理员、志愿者和普通用户的业务权限在服务端校验。
- OCR 与模型分析只有在用户明确开启健康数据外发授权后才能调用。

## 10. 答辩常见问题

### 10.1 为什么不用前端身份切换？

身份切换无法证明真实鉴权，也容易把权限逻辑留在客户端。当前版本只保留真实注册、登录和服务端角色授权，三门户由同一账户体系进入。

### 10.2 为什么地图有时不显示路径？

路径必须来自高德道路规划。服务不可用时宁可只显示资源和现场位置，也不画可能穿越建筑或水面的伪路线。

### 10.3 系统如何避免同一 AED 被多人同时占用？

设备预留在事务中完成，实体带版本号；求救者还有活动救援锁。冲突请求只能有一个成功，其余请求重新匹配或失败回退。

### 10.4 OCR 和模型是否直接给出诊断？

不会。OCR 识别报告文字，模型整理报告中已有信息并输出一般性说明，用户复核后入档。界面持续提示结果不能替代医生诊断。

### 10.5 没有预置数据如何比赛演示？

演示前用三组临时手机号正常注册，在管理员端授权角色，再通过真实操作产生设备、救援、体检和投稿记录。这样评委看到的每条数据都有明确来源和跨端状态变化。

## 11. 演示结束

退出全部账户，清理现场临时数据库和上传媒体，关闭临时 OCR/模型密钥，保留构建日志和验收记录。源代码仓库不写入现场账号、密码或业务数据。
