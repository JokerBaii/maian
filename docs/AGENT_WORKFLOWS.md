# 资源协同与轻量助手

本期保留现有 Spring Boot 3.5 / Spring AI 1.1.8，新增事件驱动的资源协同和应用导航助手。

## 资源协同

入口：**我的急救设备 → 资源协同**。设备操作菜单提供“报告设备故障”；已有救援关联的故障设备修复后，可选择“确认修复并恢复”。

设备停用、故障上报、重新启用、资料更新、审核通过、移动设备位置恢复时，在同一业务事务中写入协同任务。事务失败时设备变更和任务一起回滚。任务表独立保留设备名称和事件信息，设备删除后仍能查看历史。

后台协调器按以下工具检查事实并推进任务：

1. `inspectDevice`：读取当前状态、开放时段、有效期和位置新鲜度。
2. `inspectRescueImpact`：检查原设备与救援的当前关联及志愿者接单情况。
3. `findAlternatives`：查询最多三个替代候选的估算 ETA；此时不预留设备。
4. `coordinateResources`：在事务中重新检查条件，执行允许的资源调整。

开启模型时通过 Spring AI `@Tool` 调用工具；关闭模型、模型失败、调用超时或模型未完成工具执行时，使用同一套业务工具兜底。页面分别显示“AI 工具协同”“规则协同”“规则兜底”，不把规则执行伪装成模型执行。

### 执行边界

- 尚无志愿者接单且仍在原匹配时限内：释放失效关联，重新匹配候选；无资源时保留等待流程，继续由原调度器重试，不延长原截止时间。
- 已有人接单或设备仍待归还：保留原任务、预留与保管关系，产生需要人工核实的结果；不自动改变取用安排。
- 设备故障后禁止确认取用。设备管理方确认修复后恢复原预留，相关人工核实记录随之更新。
- 故障设备取消占用或归还后仍保持停用，直到管理方主动确认启用。
- 资源恢复可用时，检查附近最多 20 个等待任务；实际匹配仍经过原有事务锁和资格校验。
- 原救援调度器独立检查尚未接单任务的设备可用性并重新匹配；模型调用使用独立线程池和调度器，不进入 SOS 请求链路。
- 实时调度器先移除失效设备但尚未找到替代资源时，协同记录仍保留待跟进提醒。后续正常调度匹配成功或等待救援结束后，记录自动更新结果。
- 已接单设备的故障记录在修复后关闭；先归还再修复、先提交修复事件再归还均可核对，不要求原预留关系仍然存在。归还后尚未修复的设备继续保留提醒。
- ETA 继续使用现有估算模型，候选预览不代表已经规划了道路路线。

任务和步骤写入 MySQL，通过页面每 3 秒刷新展示真实过程。救援状态调整沿用原 SSE 通知。执行中断的任务在租约到期后可恢复；执行操作按任务幂等，失败任务可由设备所有者重新检查。

独立的结果跟进器默认每 5 秒核对最多 30 条待跟进记录，按上次检查时间轮转。跟进仅检查业务事实并更新协同记录，不调用模型、不重新分配救援，也不会反复追加相同的过程步骤。可通过 `app.agent.follow-up-initial-delay-ms`、`app.agent.follow-up-interval-ms` 调整运行间隔。

### 权限与数据

- 我的协同记录只返回本人登记设备产生的任务。
- 救援关联记录仅向求救者和已经接单的志愿者开放。
- 模型工具返回受控状态、候选数量和估算 ETA，不外发求救者身份、症状、联系方式或精确位置。
- 工具结果以外的模型自由文本不用于执行操作，也不作为页面事实展示。

## 脉安助手

入口：**首页 → 脉安助手**。

支持查找通知设置、隐私设置、心率阈值、紧急联系人、穿戴绑定、设备管理和资源协同进展，以及按主题推荐已审核、已发布的文章。返回页面卡片，点击后进入真实页面；设置需要用户在对应页面修改。

助手默认采用站内检索。用户打开“允许 AI 理解本次输入”后，才允许本次输入发往模型服务。模型通过 `findAppPage`、`searchApprovedArticles` 查询真实内容；模型未启用或调用失败时降级为站内检索。空目录明确显示未找到内容，不生成虚构文章。

客户端对卡片目标页面使用白名单，服务端工具只读，不允许模型更改设置、授权角色或发起救援。每个任务最多调用 8 次工具，模型执行窗口为 12 秒，并限制并发和排队长度。

## 配置与验证

默认无需模型密钥即可验证规则协同及站内检索。启用 AI 工具调用沿用服务端配置：

```bash
export APP_AI_ENABLED=true
export OPENAI_API_KEY='your-model-key'
export OPENAI_MODEL=deepseek-chat
```

数据库由 Flyway `V19__resource_coordination.sql` 创建任务和步骤表，`V20__coordination_follow_up_index.sql` 为持续跟进查询添加索引。新增接口：

```text
POST /api/v1/emergency-devices/{id}/fault
GET  /api/v1/coordination-tasks/mine
GET  /api/v1/coordination-tasks/rescue/{id}
POST /api/v1/coordination-tasks/{id}/retry
POST /api/v1/assistant
```

建议用测试设备与测试呼救演示：先审核两台 AED；呼救匹配其中一台后，在设备所有者页面上报故障，查看实时重新匹配及协同记录。第二轮先由志愿者响应，再上报故障，展示人工核实、确认修复及保管关系保留。

```bash
npm run type-check
npm test
npm run build:h5
cd server && mvn test
```

第二轮集成增加以下验证：

- 状态回归：实时调度先移除故障设备但无替代资源、后续匹配成功、等待任务取消、归还后修复及修复入队后归还。
- Spring AI 工具协议：使用真实 `ChatClient`、OpenAI 协议适配器和 `@Tool` 执行器，通过本地模拟 HTTP 模型响应验证多轮工具调用、顺序约束、未完成执行时的兜底，以及页面结果只采用工具数据。
- 应用接口闭环：真实注册与 JWT 鉴权、故障接口提交事务、后台 Agent 处理、救援设备替换、过程记录读取及越权拒绝；数据库使用 H2。

前端类型检查、21 项前端测试、40 项后端测试、服务端打包和 H5 构建通过。第一轮另已验证 iOS App 资源、微信小程序构建，以及浏览器中的助手跳转、设置定位、故障上报和过程展开。模型协议测试采用本地模拟响应，线上模型服务与 MySQL 实库迁移仍需配置对应服务后联调。
